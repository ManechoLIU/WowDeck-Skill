# Transferable presentation patterns

Use these patterns to diagnose a presentation and choose a correction. The short examples below are synthetic teaching examples, not customer cases or user transcripts. Apply the current audience, material, and explicit request; do not copy a fixed industry, palette, page count, or narrative sequence.

## Patterns that help

### Build continuity around the work

**Use when:** Several product capabilities need both orientation and a memorable demonstration.

**Action:** Keep an overview spatially stable; focus a relevant region in place, show the concrete work/output, explain its significance, and reconnect when useful. Preserve the named object across steps rather than substituting unrelated cards.

**Synthetic example:** A document-review map focuses the source-check step, opens the source beside a revision, then returns to the map with the approved state visible. A separate output board explains what is ready to reuse.

**Check:** The viewer knows where they are, what changed and why. Remove repeated returns that add ceremony, and use other routes when a hub does not help.

### Connect product experience to business meaning

**Use when:** The audience needs to understand a product or an otherwise invisible working process.

**Action:** Start from a recognizable task. Follow the same person and business object through supported actions to an inspectable output. Pair a relevant, permitted product image or diagram with the point it explains. Explain the operational significance of the output without inventing measured results.

**Synthetic example:** A request becomes a draft, a person reviews it, and the accepted item is saved. A workflow diagram can explain the handoff; a focused interface detail can explain the review action. Neither proves a reduction in staff time.

**Check:** The audience can explain what happens, what is produced, and why it matters. Retire any media or interaction that adds complexity without improving that explanation.

### Make visual relationships carry meaning

**Use when:** A process, comparison, hierarchy, or transformation is easier to understand spatially.

**Action:** Choose the relationship first, then its layout. Keep callouts near their exact referent and preserve enough context to read the evidence. Vary composition inside one accepted visual system.

**Synthetic example:** Use aligned rows for like-for-like comparison and a directed path for sequential work; use a local focus change to explain a detail in an interface.

**Check:** The relationship remains clear in a static screenshot and reduced-motion mode. A decorative effect is not evidence of improved understanding.

## Failure patterns and corrections

| Failure pattern | Correction | Acceptance and limits |
|---|---|---|
| Generalisation removes concrete making guidance, leaving only prohibitions and bookkeeping | Keep scene families, subject research, outcome-first demonstrations and motion techniques available while making defaults adaptable. | Test the resulting deck, not the number of rules. |
| “Business audience” erases the product into management slogans | Explain the actual task, action, response, output and next use in business language. | The listener can describe the operation as well as the relevance. |
| Image/SVG/layout/animation quotas act as a quality score | Keep source inventory separate; ignore decoration and inspect rendered meaning, legibility and motion. | CSS diagrams and deliberate typography remain legitimate. |
| A browser tab is opened and treated as verification | Navigate, capture, inspect, replay and check actual output; preserve evidence. | Opening and page-loading alone prove no visual acceptance. |
| Full-slide backgrounds alternate light and dark to manufacture rhythm | Keep one canvas polarity; vary composition, scale, spacing, local surfaces, and semantic motion. | Inspect every slide in a rendered gallery; a config flag alone is insufficient. |
| A question about the existing palette is treated as approval to replace it | Explain the current choice and preserve the latest accepted baseline until an actual change instruction or resolved material need exists. | Applies to revisions. A new explicit decision can replace the baseline. |
| A named customer or example is confused with the entire target market | Separate product category, primary audience, venue, and illustrative example before writing the opening. | Check the opening, examples, and ending for accidental audience narrowing or widening. |
| The deck lists features or generic benefits but does not explain the product | Show concrete actions, outputs, a coherent usage journey, and the supported business significance. | A listener should be able to explain both the operation and its relevance. |
| A request for rich visuals produces an initialized HTML shell, repeated text cards, or only generic fades | Plan real assets or diagrams, visual relationships, and semantic motion in the storyboard; inspect representative rendered screens early. | Map explicit requests to actual implementation and evidence. Do not impose image or animation quotas. |
| Production status, debugging, or author instructions dominate a business talk | Keep production notes internal and write audience-facing language. Preserve material qualifications in an understandable form. | Does not permit invented capability, customers, or outcomes. Technical reviews may require technical detail. |
| Planned durations are reported as proof that a talk fits the time limit | Budget speech, demo, reveals, transitions, and pauses, then rehearse continuously. | Timing arithmetic is planning evidence; a completed rehearsal supports an elapsed-time claim. |
| Saving an item is expanded into unverified retrieval, editing, sharing, or publishing support | Name only the supported action and verify each downstream behavior before claiming it. | An interface affordance or saved-state label is not proof of a complete subsequent workflow. |

## Maintaining reusable lessons

Keep private evidence in a local record outside the shared repository. Publish only the abstract condition, recommended action, acceptance criterion, and invalidation condition. Do not publish project or customer identities, user feedback quotations, conversation dates or identifiers, private paths, screenshots, audio/video, deck artifacts, or recognizable case narratives without separate, explicit permission for those exact materials.

Prefer synthetic examples that demonstrate the relationship without reconstructing a private case. Merge duplicate lessons into existing rules. A user preference, an observed technique, a recommendation, and runtime acceptance are different kinds of evidence; abstraction must preserve those distinctions without disclosing their private source.
